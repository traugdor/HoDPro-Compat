# Repository Policy

## Commit and code attribution

Commits in this repository do not carry AI/assistant co-author attribution. Do not add `Co-Authored-By` trailers, "Generated by," "Written with," or any similar AI-attribution line to commit messages. Do not add comments, file headers, banners, or docstrings crediting an AI tool for writing or modifying code.

## Editing design documents

When a design decision in a document changes, fully replace the changed portion with the new decision. Don't leave the old mechanic in place with an explanation of what changed or why it's now superseded — just fix it and move on. Don't over-explain an old mechanic that's no longer relevant. The document should always read as the current state of the design, not a changelog of how it got there.

## Asking the user questions

Before asking a question, check whether the answer is already obvious from context — the conversation so far, the document's own scope or structure, or plain logical deduction (e.g., a broken-bones-only review document obviously doesn't need an unrelated mechanic folded into it; that's not a judgment call, it's just scope). If it's obvious, don't ask it — just state what you're doing and why. Never narrate the skipped question ("I was going to ask X but figured Y was right") — just say the choice: "I am doing [choice] because [reason]."

This does not lower the bar for genuine judgment calls. Numeric balance values, subjective design preferences, and anything with more than one reasonable answer still get asked, one at a time, same as always. The test is whether a reasonable person would see only one sensible answer given what's already been established — not whether an answer merely seems likely or convenient.

## Following explicit instructions

When the user gives an explicit, unambiguous instruction (a specific value, a specific domain/path, a specific approach), do not substitute a different answer based on inference, memory, or pattern-matching (e.g. folder layout, naming conventions) unless that inference has actually been verified against real evidence — the shipped assets, the decompiled source, a working example already in the codebase. An instruction is the starting point to verify against, not a claim to second-guess.

If verification turns up something that contradicts the instruction, that contradiction has to survive contact with the strongest available evidence before it's presented as a correction — not just be plausible. Don't present an unverified inference to the user as settled fact ("here's what's actually true, adjust course"). If solid evidence really does contradict the instruction, say so plainly and show the evidence; otherwise, just follow the instruction.

Existing, already-working code elsewhere in this repo is itself strong evidence and outranks a guess based on naming/folder patterns. If the codebase already does something consistently (a domain prefix, an API call shape, a pattern repeated across many files), check for that precedent before concluding it should be done differently — don't relitigate something already established just because a surface-level pattern (like a folder name) suggests otherwise.

## Code comments

Write comments as if for a future maintainer, not a chat reviewer. Don't narrate what changed, why an earlier alternative was rejected, or that something was "reworked per feedback" — describe the current contract only: what the code guarantees, real preconditions/gotchas, non-obvious domain reasoning (engine quirks, workarounds, why a value is what it is). If a comment restates what the code already makes obvious, cut it; if it buries one useful fact in several sentences of justification, keep the fact and drop the rest. This applies to all new comments going forward — don't wait for a `/comment-cleanup` pass to write it right the first time.

Live debugging narration — what was just tried, what failed and why, what got confirmed by a test, what's still uncertain — belongs only in chat responses, never in code or comments. This applies during active back-and-forth debugging especially, since that's exactly when this kind of narration is being generated turn by turn and is most likely to leak into an edit. Before writing any comment, ask whether it describes the code's current contract, or whether it's actually explaining a decision relative to a prior attempt, a rejected approach, or something confirmed during testing. If it's the latter, that content goes in the response to the user, not in the file. A comment should read the same whether the reader saw the whole debugging session or none of it.

## Handling bug reports

When the user reports a problem with the code, take the report at face value — it is not up for interpretation, and it is not evidence that needs corroborating. Don't suggest that what they saw or experienced was wrong, mistimed, or a misunderstanding, and don't hand-wave it away with an alternate explanation. The report itself is the confirmation; there is no need to add debugging output and ask the user to test again just to verify it before starting real work — that costs the user another full round trip through the game for something already established.

Instead, ask what steps were actually taken to produce it, if that's not already clear, then go find the cause directly: read through the code responsible for that behavior from start to finish, and reason out what the code actually does versus what the user reported and what should have happened instead. Fix the code so the outcome the user expected is the actual outcome. Debug logging is a last resort for when reading the code genuinely can't resolve the question — not a first step, and not a substitute for working through the logic yourself.

## Building while the game is running

The build's DLL copy step fails with a file-lock error (MSB3027/MSB3021) whenever Vintage Story or the Visual Studio debugger still has the mod DLL open. Don't just report the lock and wait for the user to confirm they've closed it — poll for it yourself (retry the build on a short interval) until it succeeds or a reasonable timeout is reached, then report the actual result. The user shouldn't have to be a manual retry loop for something the agent can just watch for.

## Verifying claims against the base game

Any assertion about the base game — a class, item, mechanic, file, or behavior — must be verified against the actual decompiled source or shipped assets before being stated as fact. Never state something about vanilla behavior from memory or plausibility alone.

If existing documentation contains a base-game claim that looks made up or unverified, check it before relying on it or building further on top of it. Tell the user plainly that the claim needs (or needed) double-checking, and correct the documentation once verified.

If a base-game claim turns out to have been wrong, apologize for the wasted time, tokens, and credits that resulted, then fix it.

If this instruction can't be followed for some reason, say so directly and explain why in plain, concise terms — don't quietly skip it.

## Locating files

Do not use `find` (including `find.exe` via Bash/PowerShell) to search the filesystem — it pegs the CPU, especially when the location is already known. Vanilla decompiled source lives under `./VSDecompile`; the mod's own C# lives under `Remedy And Ruin/Remedy And Ruin/Remedy And Ruin/GameEngineTweaks`; the mod's assets live under `Remedy And Ruin/Remedy And Ruin/Remedy And Ruin/assets/remedyandruin`; the real installed game assets live under `C:\Users\joelt\AppData\Roaming\Vintagestory\assets\survival` (not `assets\game`, which is mostly stripped). Use the Glob tool, or a targeted `grep -rl`/Grep tool call scoped to one of these known directories, instead.
